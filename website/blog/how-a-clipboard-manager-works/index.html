How a Clipboard Manager Works: Polling, Hotkeys and Pasting

2026-10-19 · sabaoongfx · 7 min read

A clipboard manager looks like one of the simplest programs you could write: remember what was copied. In practice each operating system answers four questions differently. How do you notice a change? How do you grab a hotkey nobody else is using? How do you paste into another program? And how do you do all of it without freezing the window? This post walks through how Open Clipboard Manager handles each, and why the answers differ so much between Windows, Linux and macOS.

Noticing that something was copied

None of the three systems gives a background application a dependable “the clipboard changed” callback that works everywhere, so the app polls: the Tk thread checks every 300 ms. The trick is making each check nearly free, which means reading a small change indicator instead of the clipboard itself, and only fetching the contents when that indicator moves.

  • Windows keeps a sequence number that increases every time the clipboard changes, available through GetClipboardSequenceNumber. Reading it takes no lock on the clipboard and copies no data.
  • macOS offers the same idea as NSPasteboard.changeCount, an integer that goes up with each change.
  • Linux has no counter. The app runs xclip (X11) or wl-paste (Wayland) and hashes what comes back, then compares the hash with the last one. It is more work per check, which is why Linux is the platform where polling costs the most.

A 300 ms interval is a compromise. Shorter would catch two quick copies in a row more reliably but spend more time asking; longer would save a little power but sometimes miss the first of two fast copies. Copying twice within a third of a second is rare enough for people, though scripts can do it.

A global hotkey

A hotkey that works from any application is the part that differs most between systems, so the listener runs on its own thread and never blocks the window.

  • On Windows the thread runs a message loop. Ordinary combinations can use RegisterHotKey, but Win+V is reserved by Windows itself, so the app installs a low-level keyboard hook that swallows the keys before Windows sees them. It also taps an unassigned key so the Start menu, which opens when the Windows key is released alone, stays closed.
  • On Linux it uses its own X11 connection through python-xlib to grab Super+V.
  • On macOS it registers the key with Carbon’s RegisterEventHotKey, which is delivered through the app’s event loop. The combination is Ctrl+Cmd+V, since Cmd+V is the system Paste shortcut.

Wayland is deliberately not on that list. Its security model does not let applications listen for keys while another window has focus, so there is nothing for the app to grab. The workaround is to bind a shortcut in the desktop environment to run the app with --show.

Keeping threads apart

Tk is not thread-safe, so only one thread may touch the interface. The tray menu, the hotkey listener, the image encoder and the single-instance listener all run elsewhere, and none of them calls into the UI. Instead each posts an Event to a queue, and the Tk thread drains the queue every 100 ms. This one rule removes a whole class of bugs: no locks around widgets, no random crashes when the tray menu and the window update at the same moment.

Images follow the same pattern. When an image arrives it is hashed and written as a PNG on a worker thread, so a large screenshot never stalls the window, and only then does the finished entry reach the Tk thread to be added to the list.

One copy of the app

Two copies of a clipboard manager would fight over the hotkey and record every entry twice, so the app makes sure only one runs. The running copy listens on a loopback port and records the port number in the data folder. Starting the app again, or running it with --show or --settings, connects to that port and asks the existing copy to open its window, then exits. This is also what makes the Wayland workaround possible: the desktop shortcut just runs the program again.

Pasting into the previous window

When you open the popup with the hotkey, the app remembers which window had focus. Choosing an entry puts it back on the clipboard, hides the popup and sends a paste keystroke to the remembered window. The mechanism is again per platform: Win32 calls on Windows, xdotool on X11 and wtype (or ydotool) on Wayland, and on macOS a synthetic keystroke, which needs the Accessibility permission under System Settings → Privacy & Security. If the popup was opened from the tray, there is no previous window, so the app only copies.

Where history lives

History is a JSON file in the data folder, with images stored as PNG files beside it: %APPDATA%\winclipman on Windows, ~/Library/Application Support/winclipman on macOS and ~/.local/share/winclipman on Linux. Nothing is sent anywhere. The same folder holds your copy of actions.json.

Why Python and Tk

A clipboard manager spends nearly all its time idle, so raw speed matters less than low overhead and easy packaging. Python with Tk gives a native-feeling window with no bundled browser engine, the operating-system calls are a few lines of ctypes on Windows and a bridge to PyObjC on macOS, and PyInstaller turns the result into a single file. The tests use only unittest, run on all three systems in CI, and use a temporary folder so they never touch real history.
