How to Check What an App Sends Over the Network (Without Taking Anyone's Word)

2026-10-11 · sabaoongfx · 3 min read

Every app makes claims about privacy, and most of them are impossible for a normal person to verify. But you can look. Network behaviour is one of the few things about software that can be observed from the outside, and the basic checks take minutes. This guide goes from quick to thorough. We encourage you to use it on our app, too.

Level 1: see open connections

The fastest check is to list which programs have network connections right now.

  • Windows. Open Resource Monitor (search for it) and look at the Network tab, which lists processes with network activity and the addresses they talk to. In a terminal, netstat -ano lists connections with the owning process ID, which you can match to the PID column in a task manager.
  • Linux. ss -tupn lists TCP and UDP sockets with the process attached, and lsof -i does something similar. You may need elevated rights to see other users’ processes.
  • macOS. lsof -i works there too, and the built-in nettop shows live per-process traffic.

Start the app you want to test, wait a minute, and run the command. Search for its name or PID. If it has no connections while idle, that is a good sign. Note that a brief check can miss traffic that happens only at certain times.

Level 2: watch over time

Some apps send data only occasionally, such as an update check on launch or a daily ping. Watch the machine-wide graph in your task manager with the app running and everything else closed (how to read it). Then repeat the connection check at intervals. A firewall that prompts you the first time a program tries to connect out gives you a log of each attempt. Examples include the Windows firewall in advanced mode, Little Snitch or LuLu on macOS, and OpenSnitch on Linux.

Level 3: capture the traffic

For a definite answer, capture the packets. Wireshark runs on all three systems. Start a capture, launch the app, use it for a while, then filter by the app’s traffic. Even when contents are encrypted, you can see who it talks to (addresses and domain names from DNS lookups), how often and how much. Be aware that you are looking at metadata: with modern encryption you can see that a program sent 40 KB to an analytics domain without reading what it said.

Capturing can expose your own sensitive traffic to anyone with access to the capture file, so do it on a quiet machine and delete the file afterwards.

How to interpret what you see

  • No traffic at all. The most believable result for a local tool. Check also during actions like opening links, which should hand off to your browser.
  • Update checks. Usually acceptable if they are disclosed, infrequent and documented.
  • Connections to ad, analytics or tracking domains. A red flag for a tool that has no reason to send usage data.
  • Large upload. Worth understanding before you use the tool further.

What this can't prove

Observation shows what happened while you watched. A program could behave differently later, on another machine, or only when it detects it is being monitored. That is why source code matters alongside testing: reading or searching the code tells you what is possible, and testing tells you what is happening. For Open Task Manager, you can do both; our comparison post lists what the code does and doesn’t include. If you find something we have missed, please open an issue.

Taking five minutes to look turns privacy from a promise into something you checked.
