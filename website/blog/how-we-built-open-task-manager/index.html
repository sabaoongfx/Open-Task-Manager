How We Built Open Task Manager: One Rust Core, Two Interfaces

2026-10-11 · sabaoongfx · 3 min read

Open Task Manager looks like a single app, but it is really three pieces that share one engine. This post explains how they fit together and why we made the choices we did. Some are standard practice and some are deliberate compromises, and we'll flag which is which.

A workspace with one core

The project is a Cargo workspace with three crates:

  • core/ (otm-core). All data collection lives here. A Monitor struct owns the sysinfo handles and the state needed to compute rates, such as disk throughput and the running CPU time per app. Its snapshot() returns everything the interface needs in one go. It also holds the code for the Services and Startup apps tabs, the disk scanner, and the types that are sent to the interface.
  • src-tauri/. The desktop shell. It is mostly thin command wrappers around the core, with the monitor held in shared state behind a lock.
  • tui/ (otm). The terminal UI, built with ratatui and crossterm, which calls the same core functions directly.

The rule we follow is: put new backend logic in the core, then expose it from both front ends. That keeps the desktop and terminal versions from drifting apart, and it makes the Rust code the single place where operating-system data is read.

One poll loop

On the desktop side, a single timer calls get_snapshot every 1.5 seconds. The result feeds the Processes, Performance and App history views as props. Tabs whose data doesn’t change quickly, namely Startup apps and Services, fetch once when they open. A single poll keeps the numbers consistent across tabs and means the OS is queried once per tick instead of once per component.

The mock path

Every data call in the interface branches on whether it is running inside Tauri. In a plain browser there is no backend, so the same components read generated data from a mock module instead. This has three payoffs: the frontend runs with npm run dev without a Rust toolchain, the end-to-end tests run against predictable data, and the live demo on our website is the real interface running on sample data rather than a mockup. The cost is discipline: every new backend feature needs a matching mock, or the tab will work in the real app and break in the browser.

Deliberate duplication

You will find the same table styling and right-click-menu code repeated across several tabs. That is intentional. With only a few such tabs, a shared abstraction would be more machinery than it saves, so we kept each small and independent. If the count grows, extracting a component will be the right move.

Two small CSS lessons

Row highlights need to reach the card’s true edge even when a scrollbar takes space, so the app measures the real scrollbar width once and feeds it into the layout as a CSS variable. And a table needs overflow-x: hidden set explicitly: leaving it unset lets it quietly compute to auto whenever the vertical overflow is set, which brings back a subtle horizontal scrollbar.

The terminal screens on this site are real

The terminal screenshots on our homepage are not drawn by hand. An ignored test fills otm with curated demo data, never your machine’s real processes or user names, renders its tabs into a test backend, and writes the result into the page. When the terminal UI changes, we re-run one command and the website follows.

What we would do differently

  • Filter thread entries in the core from day one (we fixed it in 0.4.1).
  • Make Services and Startup actions real earlier, instead of leaving them as interface-only.
  • Persist App history to disk.

Everything above is in the open on GitHub. If you would like to help with any of these, they are the best places to start. For why we chose this stack, see Tauri vs. Electron and Rust in the kernel.
