Running AI Models Locally: How to Estimate the RAM You'll Need

2026-10-11 · sabaoongfx · 3 min read

Running a language model on your own computer has become popular for privacy, cost and offline use. The first practical question is always the same: will it fit in memory? The honest answer is that you can estimate it with some arithmetic, then confirm it with a task manager. Be wary of web pages that give specific hardware tables without showing their working; many of those we found while researching this were generic or unreliable.

The rule of thumb

A model’s weights are a long list of numbers, and each number takes a fixed amount of space. So:

weights memory (GB) ~= parameters (billions) x bits per weight / 8

A model with 7 billion parameters stored at 16 bits per weight needs about 14 GB. The same model compressed to 8 bits needs about 7 GB, and at 4 bits about 3.5 GB. That compression is called quantization: it trades a small loss in quality for a large saving in memory.

What gets added on top

  • The context cache. While generating, the model stores intermediate values (the key-value cache) for every token in the conversation. It grows with context length, and for long contexts it can reach gigabytes.
  • Runtime overhead. The inference program itself, buffers and the operating system need room too.
  • Everything else you have open. Your browser does not shrink because a model is loaded.

A reasonable planning approach is to take the weights figure and add 20 to 30 percent for the cache and overhead, more if you use very long contexts. Treat it as a rough estimate; actual numbers depend on the model architecture and the software.

Where the memory has to be

Speed depends on where the weights live. On a computer with a dedicated graphics card, the weights ideally fit in the card’s own memory (VRAM), which is fast but limited. On machines with unified memory, such as many recent laptops, the processor and graphics share one pool, so total RAM is the limit. Models that don’t fit can spill into ordinary RAM or even onto disk, which works but can be many times slower.

This is why memory prices matter for this use case in particular (the 2026 crunch): the capacity you need is set by the model, and it is the part of the machine you can’t easily trade away.

Check it in a task manager

  1. Close what you can and note your baseline memory on the Performance tab.
  2. Load the model and watch the memory chart. The difference is its real footprint.
  3. Start a long conversation and watch it grow. That slope is the cache.
  4. If memory approaches the limit and disk activity jumps, the system is swapping and generation will crawl (diagnosing a busy disk).
  5. Check the CPU view. On machines without a suitable graphics card, inference uses the processor heavily, so expect sustained high load on many cores.

Remember that one program may appear as several processes, so look at the grouped total. And since resident memory counts shared pages, a memory-mapped model file may show differently in different tools (why).

Practical choices

  • If memory is tight, choose a smaller model or a more aggressive quantization before buying hardware.
  • Shorten the context you actually need.
  • Close memory-hungry programs such as browsers while the model runs.

The core idea is simple: the model’s size is a number you can compute, and the task manager is how you verify it. Do both before you spend money.
