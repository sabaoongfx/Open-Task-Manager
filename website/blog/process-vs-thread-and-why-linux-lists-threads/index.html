Process vs. Thread: Why Some Linux Monitors Show Thousands of Entries

2026-10-11 · sabaoongfx · 3 min read

If you have used a monitor on Linux and wondered why it listed thousands of entries and more memory than your machine has, you may have met the process-versus-thread problem. It is a good example of how the same data can be read two ways. We hit it ourselves: versions of Open Task Manager before 0.4.1 showed exactly this on Linux.

Two ways to do more than one thing

A process is an isolated running program with its own private memory. A thread is a path of execution inside a process. Threads of the same process share its memory, which makes them cheap to create and lets them cooperate easily, but also means a bug in one can affect the others.

A single-threaded program can only do one thing at a time. A multi-threaded program can, for example, keep its interface responsive while downloading a file on another thread. Modern apps routinely have dozens of threads, and a browser or game may have hundreds.

How Linux represents them

Linux treats both as “tasks” internally. Each thread gets its own ID in the kernel, and the first thread of a process is the one whose ID is shown as the process’s PID. In the /proc filesystem, threads appear in a per-process folder. Some libraries that list processes on Linux walk that data in a way that surfaces each thread as an entry of its own.

Open Task Manager reads its data through the sysinfo crate, and on Linux that library can list every thread as a separate process. Before version 0.4.1 we passed all of them through. The catch is what each entry reports: because threads share memory, each one reports the memory of the whole process. Add them up and you count the same memory many times.

What goes wrong

  • Inflated process counts. A machine with 300 real processes can show over a thousand rows.
  • Impossible memory totals. Summing per-row memory, as a Users view does, can exceed the physical RAM installed.
  • Misleading sorting. A process with many threads can appear many times near the top.

The fix was straightforward: skip entries that the library identifies as threads when building the snapshot, which version 0.4.1 does. Process counts and memory totals dropped as a result and now line up with what the machine really has. It is worth knowing about because other tools still make the same mistake.

How to tell if a tool is doing this

Compare the monitor’s total against the machine. Add the memory of the largest groups and see whether it plausibly fits in your RAM. Compare the process count with the output of a basic command such as ps -e | wc -l, which counts processes rather than threads. Large mismatches suggest threads are being listed. Some tools offer a toggle to show or hide threads, and htop, for example, can show them as a tree you can switch off.

Why you might want threads anyway

Showing threads is not wrong; it answers a different question. If you are debugging why one program is slow, a per-thread view can show that a single thread is pegging a core while the others idle. That is invaluable for developers. For everyday use, though, a process-level view with accurate totals is what people expect from a task manager.

For the related question of what a percentage of CPU means across threads and cores, see CPU usage explained. If you are new to the vocabulary, start with what a process is.
