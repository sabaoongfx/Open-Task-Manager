Rust Is Now a Permanent Part of the Linux Kernel. Here's What That Means for System Tools

2026-10-11 · sabaoongfx · 3 min read

In December 2025, at the Maintainers Summit in Tokyo, Linux kernel developers reached a consensus that Rust in the kernel is no longer an experiment. Miguel Ojeda, who leads the Rust for Linux effort, sent a patch removing the “experimental” warnings from the kernel documentation and summed it up in one line: “The experiment is over, meaning Rust stays.” For a project that began as a curiosity a few years earlier, that is a large shift in status.

What actually changed

It is worth being precise, because headlines made this sound bigger than it is. Nobody is rewriting the kernel in Rust. The C code that makes up almost all of Linux is staying. What changed is the policy: Rust is now a supported, permanent way to write new kernel code, mainly drivers and other self-contained subsystems, and the project will keep investing in the build tooling and the abstractions that make it work.

Ojeda was also careful to say this does not mean everything works for every kernel configuration, processor architecture or toolchain. A lot of work remains, and some maintainers still have reservations about mixed-language code. Reports also note that Android 16 devices built on the 6.12 kernel already ship a memory allocator called ashmem written in Rust, so the language is running on a very large number of phones today.

Why memory safety is the point

Operating system code spends its life handling raw memory: buffers, pointers, lifetimes. In C, a single mistake such as reading past the end of a buffer or using memory after it has been freed can become a crash or a security hole. Rust’s compiler rules out entire categories of those mistakes before the program runs, without needing a garbage collector. That trade is the reason kernel developers were willing to take on the cost of supporting a second language.

The same logic applies one level up. A system monitor reads untrusted, constantly changing data from the operating system: process names that can contain any bytes, files that vanish between listing and opening, counters that wrap. A tool in a memory-safe language can still have bugs, but a misread buffer is much less likely to become something worse.

What it means for the tools you use

For the ordinary person running Linux, nothing visible changes today. Over the next few years you may notice more drivers and utilities written in Rust, and fewer of the memory-corruption bugs that fill security advisories. For tool authors, the signal is that Rust is a safe long-term bet: if the most conservative large codebase in open source is committing to it, a smaller project can too.

That is part of why Open Task Manager is built the way it is. Its data-collection library, otm-core, is written in Rust and shared by the desktop app and the terminal UI, so the code that touches your operating system is the code the compiler checks most strictly. The interface above it is TypeScript and React inside a native Tauri window. If you want a closer look at that split, how we built Open Task Manager walks through it.

What to watch

  • Driver coverage. The first real test is how many in-tree drivers adopt Rust, and how smoothly they are maintained.
  • Toolchain stability. The kernel depends on specific compiler features, so how quickly those become stable matters for distributions.
  • The human side. Mixed-language projects live or die on whether maintainers of different languages can work together. The summit outcome helps, but it is not the end of that conversation.

The takeaway is modest and useful: Rust in the kernel is no longer a bet on the future, it is part of the present. That is good news for anyone who cares about the reliability of the software that sits closest to the hardware.
