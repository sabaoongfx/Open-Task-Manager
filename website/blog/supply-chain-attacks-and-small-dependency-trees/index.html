Shai-Hulud and the Case for Small Dependency Trees

2026-10-11 · sabaoongfx · 3 min read

In September 2025, attackers compromised the accounts of maintainers of popular npm packages, including well-known utilities such as debug and chalk, and published tainted versions. A related campaign, nicknamed Shai-Hulud after the sandworms of Dune, went further: its install script stole developer credentials and used them to republish infected versions of the victims’ own packages, reportedly reaching more than 180 packages. Security firms described it as among the first self-replicating supply chain attacks.

In November 2025 a second wave, usually called Shai-Hulud 2.0, moved the malicious code to the preinstall stage, widened its reach to Linux, macOS and Windows, and added further spreading mechanisms. Packages uploaded between November 21 and 23 reportedly affected projects from companies including Zapier, PostHog and Postman. Counts and details vary between security vendors, so treat exact numbers as approximate.

Why this matters even if you never use npm

Most modern software is assembled from hundreds of third-party packages, in every language. When you install an app, you inherit trust in every one of them. A compromised package doesn’t have to be famous; it only has to be somewhere in the chain. And for a developer, the first thing a malicious install script reaches is the credentials on the machine that is building the software you will later download.

Where a system monitor stands

A system monitor is a sensitive kind of program: it reads every process on your machine. That is a strong argument for it to have few moving parts. In Open Task Manager’s case, the Rust workspace declares only a few direct dependencies: sysinfo, serde, Tauri and ratatui. The web interface lists six runtime packages (React, ReactDOM, the Tauri API and opener plugin, an Inter font package and an icon set), with the build tools kept separate as development dependencies. Lockfiles for both ecosystems are committed to the repository.

We should be careful about what that does and doesn’t prove. Every direct dependency brings its own dependencies, and the full tree is much larger than six or four. A short list is easier to review and gives an attacker fewer doors, but it is not immunity.

Habits that reduce your exposure

If you build software

  • Commit and use lockfiles so installs are repeatable, and review dependency updates instead of accepting them automatically.
  • Prefer fewer, well-maintained dependencies. Before adding a package for one small function, consider writing the function.
  • Avoid running install scripts you don’t need. Package managers let you disable lifecycle scripts, which blocks the mechanism these worms used.
  • Protect maintainer accounts with hardware-backed two-factor authentication and short-lived tokens.

If you only install apps

  • Prefer software from signed repositories or official releases over random download sites.
  • Keep the system updated, since many incidents are caught and fixed quickly.
  • Notice what new software does after install. A tool that has no reason to use the network but does is worth investigating (here is how).

The bigger point

Open source is not a defence against supply chain attacks; the affected packages were open source. What it does provide is visibility, because the malicious versions were found and analysed by outsiders reading public code and registries. Combine that visibility with small dependency trees and careful installs, and you reduce the odds that you are the one who finds out the hard way.
