Why Signed Package Repositories Matter (and What They Don't Protect)

2026-10-11 · sabaoongfx · 3 min read

When you run a command to install software from a repository, you are trusting a long chain: the server, the network between you and it, and the people who built the package. A signature is how that chain is verified. It is a small mechanism with a large effect, and it is worth understanding, especially since Open Task Manager publishes its own signed apt and pacman repositories.

What a signature does

A publisher holds a private key and shares the matching public key. When they publish a repository, they sign its index (and in pacman’s case, the packages too) with the private key. Your package manager, which has the public key, checks the signature before installing anything. If anyone modified the files after signing, the check fails and the install stops.

This protects you against several real risks:

  • Tampering in transit. A hostile network or proxy can't swap in a modified package.
  • A compromised mirror or host. If the server storing the files is hacked, the attacker can replace files but not produce a valid signature without the private key.
  • Silent corruption. Damaged downloads are caught.

What it doesn’t do

  • It doesn’t prove the software is safe. A signature says “this came from the key holder,” not “this is harmless.” A signed package from a malicious publisher is still malicious.
  • It doesn’t protect against a stolen key. If the signing key leaks, an attacker can sign anything. This is why keys should be kept in protected storage and rotated if exposed.
  • It doesn’t verify the first key. You must obtain the public key the first time over a channel you trust. If an attacker substitutes the key, they control what verifies.

That last point is the weakest link in every system. Check the key fingerprint against a second source, such as the project’s repository, when you add a new repository.

How our repositories work

Open Task Manager is published through GitHub Pages with one GPG key that signs both the pacman and apt repositories. When a release is published, an automated workflow rebuilds the whole site from scratch, so only the newest version is kept. The pacman package is built from source in an Arch Linux container, signed, and added with repo-add. The apt repository is built with reprepro from the release’s .deb. The apt step waits for the pacman build to succeed, so a failed build leaves the previous site untouched rather than breaking one of the repositories.

Prerelease tags are skipped entirely because the Arch version field can’t contain a hyphen. The Arch User Repository packages are prepared but not yet published, because new registrations on the AUR were closed when we set this up.

What you should do

  1. Prefer signed sources when a project offers them, rather than downloading random installers.
  2. Verify the key when you add it. Compare the fingerprint with the one published on the project page.
  3. Keep your system updated so you receive fixes, including revoked keys.
  4. Remember the limits. Signing guards the delivery, not the contents. That is why open code matters too (supply chain attacks).

Note that our Windows and macOS installers are not code-signed yet, which is a gap we have listed on the roadmap. Until then, expect a warning when you first open them, and verify downloads from the official release page.
